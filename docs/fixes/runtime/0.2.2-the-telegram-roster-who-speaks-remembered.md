## runtime · 0.2.2 · 2026-11-03 — The Telegram roster: who speaks, remembered

### Why
Telegram will not list a group's ordinary members and the bridge hands over no sender, so a complete member list can only be built from who speaks. The roster records it in the hoard, one file per chat, idempotent by message id, with admins merged from the API.

### The gap this closes

Two limits stack, and neither is ours to remove:

1. **Telegram will not list ordinary members** — the Bot API gives a bot the chat, the count, the administrators,
   and one member at a time *if the id is already known*. There is no "everyone" call.
2. **The bridge hands over no sender** — `@llblab/pi-telegram`'s programmatic inbound handler input is
   `{ kind, text?, file?, mimeType? }`; the chat id and the sender are dropped before the agent sees them, and the
   command-template bus has no `{chat_id}` or `{from_id}` placeholder.

So the honest member list is **a roster built from who speaks**, and this door is it: `record` (idempotent by
message id, so a replayed update cannot inflate a count), `list`, `show`, `chats`, and `sync-admins` (which merges
the administrators Telegram *will* give, so an admin who never speaks still appears).

The store is `<hoard>/data/telegram-rosters/<chat-id>.yaml` — one file per chat, private data, never in the public
tree (Rule 04). Every row carries its `source`: `observed`, `api` or `operator`, so a measurement is never mistaken
for a guess. **A row is never a grant**: knowing a name opens no door.

### What was proved

`bin/notify/tests/test_telegram_roster.sh` — **10 assertions, all passing**: a speaker is recorded; the same
message counts once; two chats are two files; `chats` lists both; `show` returns the row and refuses an unknown id;
an admin who never spoke is recorded with role `admin` from the API; and a record without a message id still works.

### What is still owed

The half that feeds it: the bridge must hand over `chat.id` and `from`, or a second (scribe) bot must read its own
update stream. Both roads, and the refusal of the third (a user-account client, which breaks Telegram's terms),
are written in **plan 174 §2**. Until one of them lands, the roster is fed by hand or by whatever the harness can
see — and it says so, rather than pretending to be complete.
