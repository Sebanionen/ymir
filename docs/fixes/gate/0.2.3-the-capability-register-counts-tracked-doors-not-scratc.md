## gate · 0.2.3 · 2026-11-03 — The capability register counts tracked doors, not scratch files

### Why
`find bin` counted a colleague's untracked door, so a clean `main` read STALE on that working tree — and a
well-meaning `generate` would have committed a register describing files nobody else has.

### The fault

`bin/gates/capabilities.sh` counted doors with `find bin \( -name '*.sh' -o -name '*.py' \)` — the **working
tree**, not the tree that will be committed. Untracked scratch (`bin/seat/ymir-mcp.py`, `bin/mcp/`,
`bin/seat/assets/`) therefore made a clean `main` read **STALE** on this machine, and the remedy it printed —
`bin/gates/registers.sh generate` — would have written a register **describing files nobody else has**.

That is worse than stale, and the file's own header already said so about the opposite error: *"a stale register
fails a gate and a wrong one does not."*

### What changed

The door counts **tracked** files when it is in a git tree (`git ls-files 'bin/*.sh' 'bin/*.py'`), falling back to
`find` outside one. Inventory has always counted tracked files; the capability register now matches it, so the two
registers describe the same tree — which is the whole point of one door owning both.

### What was proved

In a clean worktree at `main`, with an untracked door planted in `bin/`:

- **old script** → `STALE` (the false red that started this);
- **fixed script** → `current (652 door rows)`;
- with the probe removed → `current` again, and `bin/gates/registers.sh check` agrees.

### Why it is worth a note of its own

The trap that made this visible is the one its neighbour exists for: two registers, two generators, two gates.
This one is subtler — a register that disagrees with the tree **because the tree is dirty** teaches a hand to "fix"
it by committing work that is not theirs. A generated file must describe what is tracked, or it quietly commits
someone else's half-finished door.
